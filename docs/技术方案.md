# 技术方案

本文评估 Rummy 在线单机版的**技术栈选型**与**交互设计方案**，目标是：沉浸感强、UI 现代化、同时适配移动端与桌面端的横竖屏。

规则见 [README](../README.md)。

## 1. 结论先行

| 层 | 选型 | 理由 |
| --- | --- | --- |
| 构建 | **Vite 7** | 冷启动快、原生 ESM、子路径部署配置简单 |
| 语言 | **TypeScript（strict）** | 规则引擎状态机复杂，类型是正确性的一等保障 |
| UI 框架 | **React 19** | 生态与动画库最成熟；组件化便于拆分三套布局 |
| 渲染层 | **DOM + CSS** | 54 张牌的量级 DOM 毫无压力，且文本/无障碍/响应式全部原生 |
| 动画 | **Web Animations API + CSS Transition** | 零依赖、可中断、可与 FLIP 结合做跨布局位移 |
| 状态 | **纯函数 reducer（自研，零框架依赖）** | 规则引擎必须可单测、可回放、与 UI 解耦 |
| 样式 | **CSS Modules + CSS 自定义属性** | 主题与尺寸变量集中管理，避免运行时 CSS-in-JS 开销 |
| 测试 | **Vitest + Playwright** | 规则引擎单测 + 多视口 E2E |
| 分发 | **PWA + GitHub Pages** | 可安装、离线可用，移动端「像 App 一样」是沉浸感的关键一环 |

**核心判断：不引入游戏引擎（Pixi / Phaser / Cocos）。** 理由见 [第 4 节](#4-渲染层为什么用-dom-而不是-canvas)。

## 2. 技术栈对比

### 2.1 UI 框架

| 方案 | 体积（gzip） | 优势 | 劣势 | 适配度 |
| --- | --- | --- | --- | --- |
| **React 19** | ~45 KB | 动画生态最成熟（motion/react-spring）；社区资料多 | 需注意避免无谓重渲染 | ★★★★★ |
| Preact | ~12 KB | API 兼容 React，体积小 | 部分动画库需 alias 适配 | ★★★★ |
| Svelte 5 | ~20 KB | 编译期优化，内置过渡指令 | 动画生态弱于 React | ★★★★ |
| Vue 3 | ~35 KB | Transition 组件好用，模板可读性强 | 类型推导弱于 TS 优先的方案 | ★★★★ |
| Solid | ~8 KB | 细粒度更新，性能最佳 | 54 张牌场景性能过剩 | ★★★ |

**推荐 React**，但需要明确：**选它不是因为它快，而是因为它的动画与手势生态能显著降低「沉浸感」的实现成本**。若更看重体积，Preact + `preact/compat` 是几乎无损的替换路径。

### 2.2 样式与动画

| 需求 | 方案 |
| --- | --- |
| 静态样式 | CSS Modules（构建期作用域隔离，零运行时） |
| 主题 / 尺寸变量 | CSS 自定义属性，由 `ResizeObserver` 写入根节点 |
| 元素位移（手牌→牌桌） | FLIP（First-Last-Invert-Play）配合 WAAPI |
| 翻牌 3D | `transform: rotateY()` + `transform-style: preserve-3d` |
| 发牌序列 | 纯 CSS `animation-delay` 交错 |
| 复杂手势拖拽 | 原生 Pointer Events（不引入 hammer.js） |

不推荐 framer-motion 作为**必需**依赖：它会带来 ~30 KB 体积且其布局动画与 FLIP 高度重叠；若后期需要更复杂的编排再按需引入。

## 3. 分层架构

关键约束：**规则引擎与 UI 之间必须存在单向数据流，且 AI 与 UI 使用同一个只读视图类型。**

```text
src/
├── core/            # 规则引擎：纯函数，零 DOM、零框架依赖
│   ├── cards.ts         # 牌的定义、花色、点数、分值
│   ├── rng.ts           # 可复现随机（mulberry32），仅 core 可见
│   ├── meld.ts          # 组合合法性、王牌模拟推断
│   ├── engine.ts        # GameState + reducer，处理所有玩家动作
│   ├── scoring.ts       # 一轮/一局结算
│   └── view.ts          # toGameView(state, side) -> GameView
├── ai/
│   ├── evaluate.ts      # 基于 GameView 的启发式评估
│   └── policy.ts        # 动作选择；严禁 import core/engine
├── ui/
│   ├── layouts/         # Portrait / Landscape / Desktop 三套布局
│   ├── components/      # Card、Meld、Hand、ScoreBoard…
│   ├── animation/       # FLIP 调度、动效编排
│   └── sound/           # WebAudio 懒初始化
├── platform/        # localStorage、PWA 注册、页面可见性
└── main.tsx
```

### 数据流

```text
用户操作 ──> dispatch(Action) ──> core/engine 产出新 GameState
                                      │
                     ┌────────────────┴────────────────┐
                     ▼                                 ▼
          toGameView(state,'player')          toGameView(state,'ai')
                     ▼                                 ▼
                  UI 渲染                        AI 决策（无牌堆）
```

- **`GameState` 永不进入 UI 层**，UI 只拿到 `GameView`。这既是 AI 隔离的实现手段，也顺带避免了 UI 层误读隐藏信息。
- 每次 `dispatch` 返回一个**动作日志（Action Log）**，动画系统据此回放「这张牌从哪里飞到哪里」，避免在 UI 里重复推断移动轨迹。

## 4. 渲染层：为什么用 DOM 而不是 Canvas

| 维度 | DOM + CSS | Canvas（Pixi / Phaser） |
| --- | --- | --- |
| 54 张牌性能 | 完全够用（≪ 100 节点） | 更够用，但过剩 |
| 文本与图标清晰度 | 原生矢量 | 需处理 DPR 缩放 |
| 无障碍 / 键盘 | 原生可及 | 需完全自建 |
| 响应式布局 | CSS Grid / Container Query 原生 | 需手写布局与命中检测 |
| 3D 翻牌、阴影 | CSS 3D 原生支持 | 需 shader 或 sprite |
| 粒子 / 光效 | 弱 | 强 |
| 包体积 | 0 | 300 KB ~ 1 MB |

**结论：主场景用 DOM。** 仅当需要「胜利撒花、光晕粒子」这类效果时，叠加一层独立的 `<canvas>` 作为**纯装饰层**（`pointer-events: none`），与主体逻辑完全解耦，失败也不影响可玩性。

## 5. 响应式与横竖屏适配

这是本项目的设计重点。方案基于**「布局预设 + 容器查询 + 尺寸变量」**三层。

### 5.1 断点矩阵

以 **视口宽高比 + 最短边** 双维度判定，而非单纯宽度断点。

| 预设 | 判定条件 | 典型设备 | 布局策略 |
| --- | --- | --- | --- |
| `phone-portrait` | `aspect-ratio < 1` 且 `min(100vw,100vh) < 600px` | 手机竖屏 | 纵向三段式 |
| `phone-landscape` | `aspect-ratio ≥ 1.5` 且 `100vh < 500px` | 手机横屏 | 左右分栏，压缩纵向 |
| `tablet` | 最短边 600 ~ 1024px | 平板 | 纵向但放大间距 |
| `desktop` | 最短边 > 1024px | 桌面 | 三栏 + 场景居中留白 |
| `ultrawide` | `aspect-ratio > 2.2` | 带鱼屏 | 场景限宽居中，背景延展 |

判定用 `clamp` 无法完成，需在根节点写入：

```ts
// platform/layout.ts 概念示意
root.dataset.layout =
  h > w && Math.min(w, h) < 600 ? 'phone-portrait'
  : w / h >= 1.5 && h < 500 ? 'phone-landscape'
  : /* ... */ 'desktop'
```

用 `ResizeObserver` 监听容器尺寸写入 CSS 变量 `--card-w`、`--gap`、`--hand-h` 等，**卡片尺寸由容器反推而非硬编码**，这样从手机到超宽屏都能等比缩放。

### 5.2 对战页元素清单

对战页需要承载的固定元素（三套布局共用同一份清单，仅排布不同）：

| 元素 | 归属 | 说明 |
| --- | --- | --- |
| 局内比分 | 全局 | 双方**本局累计得分**，常驻可见 |
| 设置按钮 | 全局 | 展开菜单：**认输**、音效开关 |
| 对手头像 + 描述 | 对手 | 描述语来自 [11.2](#112-ai-难度随段位) 的 6 档 |
| 对手手牌 | 对手 | **背面朝上，仅露出一部分**，不显示数字 |
| 对手组合区 | 对手 | 已亮出的组合 |
| 牌堆 + 弃牌堆 | 中央 | 双方组合区之间 |
| 撤回按钮 | 中央 | 紧邻牌堆区 |
| 自己组合区 | 自己 | 已亮出的组合 |
| 自己手牌区 | 自己 | 正面可见，支持排序 |
| 排序切换 | 自己 | 按花色 / 按大小 |
| 操作条 | 自己 | 亮牌 / 接牌 / 弃牌 |

#### 手牌数量不显示数字

对手手牌以**卡牌背面缩略叠加**呈现，只露出一部分（约 12px 的侧边），玩家需**自己数张数**。这是刻意的沉浸感设计：

- 卡牌张数本身就是可数信息，直接标数字会把「读局面」这件事从玩家手里拿走。
- 数牌是 Rummy 的固有策略环节（估算对手手牌能接什么），保留它才能让对局有实感。
- 实现上仅为视觉呈现，`GameView` 中仍保留 `handCount` 供 AI 与结算使用，**不违反信息公平**（玩家理论上完全可数）。

> 边界：手牌数量变化（对方摸牌、出牌）需有**明确的增删动画**，否则玩家会数错并归咎于代码。

#### 组合区与牌堆的左右关系

**关键规则：双方组合区之间才是牌堆与弃牌堆，撤回按钮紧邻牌堆。** 这决定了三套布局的共同骨架。

**portrait（手机竖屏）**

```text
┌───────────────────────────┐
│ ⚙ 局内比分 32 : 47         │  ← 顶栏
├───────────────────────────┤
│ 🧑 对手描述 · 手牌背（可数）│
│ 对手组合区（可滚动）        │
├───────────────────────────┤
│ 自己组合区                 │
│ ┌─────┐ ┌─────┐  ┌──────┐ │  ← 中部：牌堆 | 弃牌堆 | 撤回
│ │牌堆 │ │弃牌 │  │↩ 撤回│ │
│ └─────┘ └─────┘  └──────┘ │
├───────────────────────────┤
│ [♠][♥][♦][♣]  ← 排序切换   │
│ 自己手牌（横向，可扇形）     │
│ [亮牌] [接牌] [弃牌]        │
└───────────────────────────┘
```

**landscape（手机横屏 / 平板横屏）**

```text
┌──────────┬───────────────────┬──────────┐
│ ⚙ ⚔ 比分  │  对手组合区        │ 对手头像  │
│          │  ─────────────    │ 描述·手牌背│
│          │  [牌堆][弃牌][↩]   │          │
│          │  ─────────────    │          │
│          │  自己组合区        │          │
├──────────┴───────────────────┴──────────┤
│ 排序切换   自己手牌区   [亮牌][接牌][弃牌] │
└─────────────────────────────────────────┘
```

**desktop（桌面）**

同 landscape 骨架，但**整体场景限宽 `max-width: 1280px` 居中**，四周由桌布纹理延展填满。桌面用手牌扇形排布，操作条固定在手牌区右侧而非下方，减少视线纵向移动距离。

> 三套布局共享同一份**区域划分**（对手区 / 中央牌桌 / 自己区），只改变这三块的方向与尺寸，因此组件内部不需要为布局写分支。

### 5.3 移动端适配细节（易踩坑项）

| 问题 | 处理 |
| --- | --- |
| 浏览器地址栏伸缩导致 `100vh` 抖动 | 一律使用 **`100dvh`**，禁用 `100vh` |
| 刘海 / 底部指示条遮挡 | `padding: env(safe-area-inset-*)`，`viewport-fit=cover` |
| 触摸误触（相邻牌） | 卡片最小命中区 **44×44px**；手牌重叠时提升 `z-index` 并放大 8% |
| 长按选中文本 | `user-select: none` + `-webkit-touch-callout: none` |
| 桌面端 hover 残留 | 所有 hover 效果包在 `@media (hover: hover) and (pointer: fine)` 内 |
| 横竖屏切换导致布局跳变 | 手牌用 FLIP 从旧位置动画到新位置，而非重排 |
| 强制横屏 | **不锁方向**，两套布局都完整可用，仅在小高度横屏时提示「建议横屏」 |

### 5.4 手牌布局算法

- **desktop**：扇形（arc），按手牌数计算总角度（最大 30°）、每张旋转角与纵向偏移，`transform: rotate() translateY()`。
- **portrait**：横向滚动 + `scroll-snap`，卡片轻微重叠（重叠量 = 可用宽 / 手牌数，但不超过 60%）。手牌增多时**优先压缩间距**，触底后再启用滚动。

### 5.5 手牌排序

手牌提供**两种排序**，以分段控件切换，选择持久化到 `localStorage`：

| 模式 | 排序键 | 说明 |
| --- | --- | --- |
| 按花色（默认） | `花色 → 点数` | 便于查找顺子。花色顺序固定 `♠ ♥ ♦ ♣` |
| 按大小 | `点数 → 花色` | 便于查找同点数组 |

- **A 的位置按"当 1 用过则置前、否则置后"会随局面跳动，一律固定为「A 最大」**，仅显示时固定，不影响 `A-2-3` 的低位组牌合法性。
- **王牌固定排在最后**，不参与主排序（它可模拟任意牌，混在有序序列中间会破坏可读性）。
- 排序在**逻辑层（`core`）不参与**，属于纯视图排序（`ui` 层 selector）。`GameView.hand` 保持发牌顺序，避免「排序影响 AI 决策」的耦合。
- 排序切换用 FLIP 做位移过渡，卡片依次错开 15ms，形成"洗牌整理"的观感。

### 5.6 不可打出卡牌的视觉反馈

当某张手牌在当前局面下**无法组合或接牌打出**时，需明确标识，避免玩家反复尝试。

- 视觉：卡片覆盖**灰色半透明遮罩**（`rgba(0,0,0,.45)`），饱和度降至 0.2，不改变卡片位置与尺寸（避免布局跳动）。
- 仍**保留可点击**（灰遮罩不等于禁用），点击时触发「抖动 + 提示」说明具体原因：
  - 「这张牌没有可组成的组合」
  - 「当前没有可接的顺子/同点数组」
- 遮罩状态由 `core` 计算的 `playable: boolean` 提供，**不由 UI 自行推断**——合法性判定必须与引擎同源，否则会出现"画着可用但实际打不出"。
- 王牌在手中时**永远不置灰**（可模拟任意牌，几乎总有出路），仅在确实无任何模拟可能时置灰。
- 遮罩需满足对比度要求：遮罩层不得导致牌面文字完全不可辨，保证玩家仍能看清自己手上是什么牌。

> 注意：灰遮罩表达的是「此刻打不出」，会随局面（对手接牌、自己摸牌）实时变化，因此每次 `GameView` 更新都要重算 `playable` 集合。

## 6. 沉浸感设计

沉浸感不来自特效堆砌，来自**空间连续性**与**反馈密度**。

| 维度 | 做法 |
| --- | --- |
| 材质 | 桌面用 SVG `feTurbulence` 生成纸纹（~2 KB，无位图）；卡面用**内联 SVG sprite**，任意缩放不糊 |
| 层级 | 统一 3 级阴影系统（贴桌 / 抬起 / 悬浮），全站复用，避免视觉噪声 |
| 空间感 | 桌面仅 `rotateX(4deg)` 级别的微透视；**触摸设备禁用透视**（影响命中精度） |
| 动效 | 发牌交错 40ms；非法操作「抖动」；出牌走弧线；翻牌 300ms `cubic-bezier(.2,.8,.2,1)` |
| 声音 | WebAudio 合成洗牌/落牌声，**必须在首次用户手势后初始化** `AudioContext`；默认开启，可一键静音并持久化 |
| 触觉 | 落牌 `navigator.vibrate(10)`，仅 Android 生效，需静默降级 |
| 状态可见 | 分数变化用数字滚动 + `aria-live="polite"` 播报 |
| 减少动效 | `prefers-reduced-motion: reduce` 时全部降为淡入淡出，**这是硬性要求** |

## 7. 关键交互设计

结合规则中的两个特殊点：

### 7.1 王牌模拟选择

- 无歧义（如 `♠5 ♠6 ♠8` + 王牌 → 只能是 `♠7`）：**不弹窗**，直接高亮候选位置并显示 `=♠7` 角标，玩家确认即完成。
- 有歧义（`♠7 ♠8` + 王牌）：在牌面上**就地展开候选**（`♠6` / `♠9` 两个幽灵牌），点选其一。避免居中模态框遮挡手牌。
- 同点数组选花色：四花色小圆点环形排布在卡片上方。

### 7.2 接牌（含对手组合）

- **触控优先点选**：先点手牌 → 再点目标组合，两步完成。
- **桌面增强拖拽**：`pointerdown` 拖起后，所有合法落点高亮；非法落点显示拒绝态。
- 向**对手**组合接牌时，落点旁即时显示 `+7 → 对手`，颜色用中性警示色（非红色，避免玩家误以为报错），明确「这张牌的分给别人」。

### 7.3 操作可逆性

回合内（弃牌之前）所有操作支持**撤销**：`core` 保留 round 内的动作栈，UI 提供撤销按钮。弃牌即提交，不可撤销。这能显著降低误触成本，是移动端体验的关键。

- 撤回按钮位置：**紧邻牌堆 / 弃牌堆**（见 [5.2](#52-对战页元素清单) 布局），与"出牌动作"的空间语义一致。
- 无可撤回操作时**禁用但不隐藏**，保持按钮位置稳定，避免布局抖动导致误点。
- 撤销范围仅限**当前回合**。跨回合不可撤销（对方已基于你的弃牌做出反应）。

### 7.4 设置与认输

设置按钮位于全局顶栏，展开为两个项：

| 项 | 行为 |
| --- | --- |
| **认输** | 二次确认后立即结束本局并判负，**必定扣分** |
| 音效开关 | 即时生效并持久化 |

#### 术语：一律称「认输」，不称「退出对局」

「退出对局」听上去是无成本的离开，会让玩家以为可以随时中止而不受影响；「认输」才准确表达这是一个**有代价的投降动作**。因此：

- 菜单项文案：**认输**
- 确认对话框标题：**认输**
- 正文需明确写出代价，例如：「认输将立即结束本局，你判负并**扣除 3 积分**。」

#### 计分口径

认输视为本局失败，用户积分 **−3**，与正常失败一致；本局比分不参与比较，也不计入任何一方的历史成绩。

**不设任何免罚情形**，包括刚发完牌、尚未进行任何一轮的情况。

理由需要区分开：[7.5](#75-对局状态持久化) 的存档已经堵死了「靠刷新换牌」这条路，所以此处要防的**不是刷新，而是认输本身**。一旦存在任何豁免（例如"未开局不扣分"），玩家便可反复「发牌 → 看手牌 → 认输 → 重开」来白嫖起始手牌，认输的代价归零。因此只要认输，就必然 −3。

> 由此带来的副作用是误触成本较高，因此**二次确认是强制要求**，且确认按钮默认焦点应落在「继续对局」上，避免回车/轻触直接确认扣分。

#### 实现要点

- 认输**不可绕过**，但**只有"手动认输"才结算扣分**。
- 刷新、关闭标签页、切后台等**非主动离开不扣分、不结束对局**——单机游戏允许随时打断与放置，见 [7.5](#75-对局状态持久化)。

### 7.5 对局状态持久化

**目标不是强迫玩家持续在线，而是堵住刷分。** 这两者的解法完全不同：前者靠惩罚离开，后者靠**让离开无法重置牌局**。

#### 规则

| 场景 | 行为 |
| --- | --- |
| 刷新页面 / 关闭后重新打开 | **恢复原对局**，进度完全一致（同一牌局、同一发牌顺序、同一手牌） |
| 切后台 / 锁屏 / 断网 | 状态保留，回来继续 |
| 手动点击「认输」 | 结束本局并**扣 3 积分**，同时**立即清除存档** |
| 对局正常结束 | 结算积分后清除存档 |

#### 为什么这样就能防刷分

刷分的本质是「重开一局以逃避不利局面」。只要**存档存在，重开就必然回到同一局面**，刷分路径自然消失，无需用扣分去惩罚离开：

- 玩家刷新 → 恢复同一牌局，手感差的手牌不会变。
- 玩家想换一局 → 只能认输，此时才付出 −3 的代价。
- 玩家想暂停 → 随便关，回来继续，无损失。

> 关键点：**扣分绑定的是"放弃这一局"这个决策，而不是"离开页面"这个行为**。

#### 存档内容

存档为完整 `GameState` 的序列化，**不是快照摘要**——否则无法保证读档后能精确复现：

| 字段 | 必要性 |
| --- | --- |
| 牌堆 / 弃牌堆 / 双方手牌 / 双方组合 | 恢复局面 |
| 双方本局得分、当前轮次 | 恢复计分 |
| 当前轮到谁、回合内已执行的动作栈 | 恢复回合与撤销能力 |
| RNG 状态（而非 seed） | 保证后续摸牌序列一致 |
| AI 强度档位 | 局内强度快照，不可因读档重新计算 |
| 存档版本号 | 支持规则变更后的兼容处理 |

- 存储介质：`localStorage`（单条目，体积约几 KB，远低于 5 MB 上限）。
- 写入时机：**纯事件驱动，不设心跳**。每次 `dispatch` 成功后同步写入一次，即「状态确实发生变化」时才落盘。
  - 是「动作后」而非「动作前」，避免崩溃时留下「已落盘但未生效」的错位状态。
  - **不需要定时保存**：单机对局的所有状态变化都由玩家或 AI 的动作触发，不存在后台自行演进的局面，因此心跳轮询没有意义，只会增加写入次数与耗电。
  - 写入为同步 `localStorage.setItem`，单次约 KB 级，性能可忽略；不必做节流或防抖，否则会丢失最后一个动作。
- 内存中的 `GameState` 为唯一真相，存档只是它的副本，不做双向同步。

#### 兼容与降级

- 存档带**版本号**。规则变更导致存档不兼容时，**直接丢弃旧档**并提示「因版本更新，上一局已结束」，不计分也不扣分。宁可少一次续玩，也不要让玩家读到错乱的牌局。
- 读档时需**校验完整性**（如手牌数 + 牌堆数 + 弃牌数 ≠ 54 则判定损坏），损坏则按上一条丢弃。
- 隐私模式 / 存储被禁用时 `localStorage` 写入会抛异常，需 `try/catch` 降级为纯内存模式，游戏仍可玩，仅失去续局能力。

## 8. AI 信息隔离的实现保障

规则要求 AI 不得读取牌堆内容。仅靠「约定不 import」不足以约束，采用**三层**：

1. **类型层**：`ai/` 只允许 import `core/view.ts` 中的 `GameView` 与 `core/cards.ts` 的公开类型。`GameState` 含牌堆字段，但 `GameView` 不包含。
2. **工程层**：`tsconfig` 中对 `ai/**` 配置 `paths` 别名白名单 + ESLint `no-restricted-imports` 禁止 `ai` 引用 `core/engine`、`core/rng`，CI 中 `tsc --noEmit` 与 lint 失败即阻断合并。
3. **运行时层**：`toGameView` 对返回对象做**深冻结**（`Object.freeze`），确保 AI 无法通过引用穿透拿到引擎内部状态。

> ⚠️ 若仅做第 1 层而把 `GameState` 作为同一对象传参，AI 仍可通过类型断言绕过。因此第 2 层是必要的。

## 10. 风险与取舍

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 动画与状态不同步 | 动画滞后于逻辑，导致操作被打断或错位 | 逻辑先行、动画可打断（`animation.cancel()`），状态是唯一真相 |
| 手牌张数不可数 | 对手手牌背仅露一部分，玩家可能数错后归咎于代码 | 增减牌必须有明确动画；`handCount` 数据始终准确，动画只是呈现 |
| 灰遮罩状态与引擎不一致 | UI 自行推断可用性，出现"显示可打却打不出" | `playable` 由 `core` 统一计算并随 `GameView` 下发，UI 只渲染不判断 |
| 排序影响对局逻辑 | 视图排序意外改变手牌顺序，进而影响 AI 或组合判定 | 排序只存在于 `ui` 层 selector，`GameView.hand` 保持发牌顺序 |
| 认输口径不明 | 实现时对是否扣分、是否计战绩有分歧 | 已在 [7.4](#74-设置与认输) 定义：一律视为失败 −3，无免罚情形 |
| 认输与存档的职责混淆 | 误以为扣分是为了防止刷新，从而对刷新也扣分 | 职责已拆分：**刷新靠存档堵**、**认输靠扣分堵**，两者互不替代 |
| 非正常退出绕过扣分 | 关标签页/刷新可能被用来重开刷牌 | **不惩罚离开**，改为落盘 + 读档：重开必然恢复同一牌局，刷分路径消失，见 [7.5](#75-对局状态持久化) |
| 存档损坏导致读到错乱牌局 | 规则变更或写入中断后牌局不可信 | 存档带版本号 + 读档校验牌数守恒；不兼容或损坏即丢弃并提示，不计分不扣分 |
| `localStorage` 不可用 | 隐私模式下写入抛异常，可能白屏 | `try/catch` 降级为纯内存模式，可玩但不可续局 |
| 三套布局维护成本 | 同一逻辑写三遍 UI | 布局层只负责**位置**，组件与交互完全复用 |
| 手牌过多时移动端拥挤 | 扇形在窄屏不可用 | 窄屏强制切横向滚动，不做扇形 |
| 音效打扰 | 移动端静音行为不可靠 | 提供显式开关，默认开启但记忆用户选择 |
| 音效与首包预算冲突 | 100 KB 预算不应被音频占用 | 全部用 WebAudio 合成（振荡器 + 噪声包络），零音频文件；`AudioContext` 在首次手势后惰性创建，不阻塞首屏 |
| i18n 文案膨胀 | 中英双语文案会扩大包体 | 字典按语言拆包懒加载；文案用 key 引用，避免在组件内写死中文字符串 |
| AI 随段位变弱引发困惑 | 玩家连败后打得更轻松，易误认为 bug | 对战页对手栏展示 6 档描述语（如「初出茅庐的对手」）；首页不展示，见 [11.2](#112-ai-难度随段位) |
| AI 强度与段位强耦合 | 段位算法变更会牵连 AI 平衡 | `policy` 只接收 `intensity` 参数，由调用方从积分映射，二者解耦 |
| React 重渲染 | 每次状态更新全量重绘牌桌 | 用 `GameView` 做细粒度 memo，卡片 `key` 绑定牌 ID |

## 11. 已定档决策

| 项 | 决策 |
| --- | --- |
| 框架 | **React 19**，体积预算放宽到 **100 KB gzip 以内**，优先效果与兼容性 |
| PWA | **做**——可安装、离线可玩、桌面图标 |
| 撤销 | **回合内可撤销**，弃牌即提交，不可撤销 |
| 音效 | **仅操作音效**，不做背景音乐；WebAudio 合成，不引入音频文件 |
| AI 难度 | **不提供手动选择，随玩家段位变化** |
| 国际化 | **中/英双语**，首页可切换 |

### 11.1 体积预算的连带影响

既然放宽到 100 KB，可以按需引入 `framer-motion`（~30 KB）完成复杂编排，但**仍不推荐**：FLIP + WAAPI 能覆盖本项目全部动效，引入第二套动画抽象会让「动画与状态同步」的风险翻倍。建议保留预算用于 i18n 文案与 SVG 素材。

### 11.2 AI 难度随段位

段位跨度为「黑铁（负分）→ 青铜 → 白银 → 黄金 → 铂金 → 钻石 ⭐️×N」，需映射到实际策略强度。**不使用段位名称硬编码**，而是由积分分段决定：

| 积分区间 | AI 强度 | 策略行为 |
| --- | --- | --- |
| < 0（黑铁） | L0 | 仅保证合法出牌，不做价值评估 |
| 0 – 149（青铜） | L1 | 贪心：优先亮出最高分组合 |
| 150 – 299（白银） | L2 | 兼顾手牌扣分，会主动接牌消耗手牌 |
| 300 – 449（黄金） | L3 | 评估「给对手接牌」的得失，规避资敌 |
| 450 – 599（铂金 / 钻石） | L4 | 加入弃牌堆推断与对手手牌概率模型 |
| ≥ 600（钻石 ⭐️+） | L5 | L4 + 保留高价值牌的长期规划 |

- 强度只影响 `ai/policy` 的评估函数权重与搜索深度，**任何强度都严格遵守 [第 8 节](#8-ai-信息隔离的实现保障) 的信息隔离**，不存在「高难度解锁读牌」。
- 实现上 `ai/policy` 接收 `{ intensity: L0..L5 }` 参数，与 `GameView` 并列传入，不读取积分本身。

#### 下跌即玩家保护

段位可能因连败从黄金跌回白银，AI 随之变弱。这是**刻意设计**：玩家打不过时对手自动降档，避免卡关。因此**不做「只升不降」的记忆逻辑**，段位与对手强度保持强耦合。

#### 积分必须明确展示

积分是玩家的**进度可视化**，不做隐藏：

- 首页与对战页均展示**当前积分**。
- 展示**距下一段位的差额**，把"还差 32 分升段"这类目标直接写在界面上。
- 段位阈值本身在 [README](../README.md) 中已公开，隐藏积分没有意义，反而剥夺了玩家的目标感与希望。
- 钻石档位同样展示进度：`距下一颗 ★ 还差 18 分`，让高分段仍有追逐目标。
- 积分可为负（黑铁），因此进度条需支持负区间，**不要用 0 作下界**。

#### 强度呈现：6 档描述语，与 AI 等级一一对应

- **展示位置**：对战页的**对手信息栏**，作为对手头像旁的一行描述。首页不展示。
- 描述与 `L0..L5` **严格一一对应**，共 6 档。用游戏化的写实描述侧面传达对手级别，而非直接报数字。
- 每档描述都会**叠加在对手身份感上**，让玩家判断"该不该冒险"。

| 强度 | 中文描述 | 英文描述 |
| --- | --- | --- |
| L0 | 初出茅庐的对手 | A greenhorn opponent |
| L1 | 初窥门径的对手 | A promising opponent |
| L2 | 旗鼓相当的对手 | An evenly matched opponent |
| L3 | 日渐老练的对手 | A seasoned opponent |
| L4 | 身经百战的对手 | A battle-hardened opponent |
| L5 | 久经沙场的传奇 | A legendary veteran |

- 描述按**语义递进**排列，玩家即使不知道 L0–L5，也能感受到强弱阶梯。
- 描述在**一局开始时快照**。用户积分仅在局末结算时变化，因此同一局内强度恒定，不存在描述中途跳变的问题。
- 描述由 UI 层根据 `intensity` 映射得出，**不回传给 AI**，避免出现「AI 知道自己被标注为弱」这类无意义耦合。

### 11.3 i18n

- 运行时用轻量方案（`Intl.PluralRules` + 自研字典），**不引入 react-i18next**（含依赖约 15 KB，对本项目文案量不划算）。
- 字典为静态 JSON，按语言**懒加载**，首包只含当前语言。
- 需要抽取的文本包括：规则文案、段位名（已定译为 `Iron / Bronze / Silver / Gold / Platinum / Diamond`，见 [README 段位表](../README.md)）、UI 按钮、王牌选择提示、对手强度描述、卡死结算说明。
- 花牌与花色符号跨语言通用，无需本地化。
- 语言选择持久化到 `localStorage`，默认跟随 `navigator.language`。

## 12. 实施顺序

1. `core`：牌与分值、组合合法性（含王牌模拟推断）、engine reducer、计分与卡死判定 —— 纯 TS + Vitest，先行跑通
2. `ai`：L0–L5 分级策略，依赖 `GameView`，用固定 seed 做自对弈回归
3. `ui`：三套布局 + 动效编排 + 王牌交互
4. `platform`：PWA、对局存档（落盘/读档/版本兼容）、段位与语言持久化、音效
5. E2E 与 Playwright 多视口验证，最后接 GitHub Pages

先做 1 与 2 的原因：本项目的缺陷几乎全部集中在计分口径与组合判定上，UI 层出问题的概率远低于此。
